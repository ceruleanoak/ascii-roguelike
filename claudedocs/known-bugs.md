# Known Bugs

Active bugs only. Review at the start of every session. When a bug is fixed, move its row into `resolved-bugs.md` (do not leave a stub here).

**Categories**: recurring root-cause families get a `[category]` tag in the bug title so new reports can be pattern-matched to a known fix shape. Check this list before debugging. Active categories:

- `[warp-divergence]` — any path that swaps `currentRoom` outside `enterExploreState` (cheat warps, demo setup, test rooms) drifting from natural room entry. Canonical fix: route the swap through `Game.applyRoomSwap()` / `wireRoomEnemies()` / `switchZoneMusic()` (main.js); never hand-copy room-entry steps into a warp. Origin: resolved #93.
- `[layer-leak]` — combat/effect code spawns into the surface world (`currentRoom.backgroundObjects`, `game.backgroundObjects`, or open-coded `GRID.COLS/ROWS` bounds) while the player is inside a hut/dungeon interior, so effects appear on the surface at the relative position instead of in the active layer. Canonical fix: route every runtime combat spawn through `game._activeBackgroundObjects()` / `game._activeEnemies()` / `game.activeRoom` / `game.activeGridBounds()` — never reference the surface room directly, never keep a divergent private copy of the routing. Enforced by the combat-file guard in `tools/check-architecture.js`. Generation code (RoomGenerator/HutSystem/DungeonSystem/etc.) is exempt — it builds a specific room. Origin: resolved #107.
- `[clock-mismatch]` — a timer value authored on one clock is advanced by, or compared against, a different clock. The project runs two: **real seconds** (player timers, the player melee list, anything stepped with raw `deltaTime`) and **double-seconds** (enemy timers and the enemy melee list, stepped with `deltaTime * PHYSICS.ENEMY_TIMER_RATE`; held-item timers, stepped with `PHYSICS.WEAPON_TIMER_RATE` — both = 2, so a data value is half as many real seconds). Symptoms are always a clean 2× or 0.5× error, which reads as "just needs tuning" rather than as a bug — that's what makes the family worth naming. Canonical fix: identify which clock the *data* was authored against, step it with that clock at the call site, and convert at any boundary where a value crosses between the two (never re-tune the data to absorb the factor — that hides the seam and breaks the next reader). Origin: resolved #88, #92, #150, #151.
- `[damage-number-desync]` — a `CombatSystem.js` call site spawns a floating damage number (or applies knockback/effects) without checking whether the paired `takeDamage()` call actually landed. `Enemy.takeDamage`/`Player.takeDamage` silently return `false`/no-op under gates (post-hit iframes, shell form, dodge, block, armor immunity, etc.), so an unchecked call can show damage that never happened. Canonical fix: capture the `takeDamage()` return value and only spawn the number / apply follow-on effects in the branch where it's truthy — the pattern already used at the player-damage call sites in `CombatSystem.js` (e.g. lines ~1259, 1400, 1477, 1641). Origin: resolved #146 (Red Warrior dodge-roll contact damage); related prior gaps: #51, #145.
- `[key-object]` — narrative/puzzle key items (Vault Key, Skull Key) repeatedly regress because of confusion over what a "key item" actually is. The correct, ratified shape: a real `Item`, spawned into the world exactly like a weapon/armor drop and picked up through the normal proximity pickup flow, just routed to a dedicated non-equipping pool (`InventorySystem.keyItemInventory`, read/spent only via `hasKeyItem(char)`/`consumeKeyItem(char)`) instead of a quick/equip slot — "implemented exactly the same as equippable items, the only difference is they are not equipped." A boolean run/room-scoped flag with no backing `Item` is *not* this pattern, even though it superficially satisfies "not equipped" — it can't render in the world or the Tab inventory overlay, which is where every regression in this family surfaced. Canonical fix: `obj.keyChar` set on the key-carrying `BackgroundObject`, spawned via `LootSystem.spawnItemDrop` on destruction, picked up into `keyItemInventory` by `InventorySystem.tryPickupItem`'s KEY branch, displayed in the Tab overlay's KEY ITEMS section (above TREASURE) built directly from that array — never a parallel flag. Origin: resolved #178 (glyph collision), #181 (drop-chance gate bypass), #190 (Vault Key wrongly migrated to a flag), #192 (Skull Key had no inventory display), #193 (both keys unified onto the real-`Item` pattern after #190's flag-only migration broke world rendering entirely).
